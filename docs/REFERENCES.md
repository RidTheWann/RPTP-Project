**Branch-likely synthetic model (recorded 2026-10-30, RPTP-REF-015):** `tests/test_instruction_branch_likely.py` defines and tests the likely-branch execution model for `BEQL`, `BNEL`, `BLEZL`, `BGTZL`, `BLTZL`, `BGEZL`, `BLTZALL` and `BGEZALL`. The approved MIPS64 Revision 5.04 entries (pages 75, 78, 80, 82, 84, 87, 89 and 91) support the encodings, the PC-relative target formed from the sign-extended 16-bit offset added to the delay-slot address, the equality/zero-test conditions, the take-only delay-slot execution with `NullifyCurrentInstruction()` when not taken, the unconditional `GPR[31] = PC + 8` link for the two link forms and the `rs = 31` UNPREDICTABLE restriction. The RPTP model compares the low 64 bits of its register representation, masks PCs to 32 bits, records no trace entry or step count for a nullified delay slot and rejects `rs = 31` fail-closed; those choices, the `$zero` suppression, the memory representation and the generated-source shape are RPTP test definitions, not hardware facts. The host CFG always records the direct target and the fallthrough as successors for a likely branch, so nullification is not a static reachability filter. The tests cover both outcomes for all eight forms, delay-slot register and memory effects, `$zero`, explicit CFG successors, deterministic generated C++ and a native differential against the oracle. The native execution harness implements the same take-only/nullification model; `runtime/tests/runtime_tests.cpp` and `tests/test_runtime_execution.py` add direct C++ cases and an independent CLI-versus-oracle differential for all eight forms, both outcomes, unconditional link writes, `$zero`, PC masking and fail-closed `rs = 31`. **ECMA-119 spec text (checked 2026-10-22):** Ecma International, *ECMA-119, 5th edition (December 2024)*, Table 8 (p. 37) assigns BP 27 to File unit size and BP 28 to Interleave gap size; §§10.1.8–10.1.9 (p. 40) define both as 8-bit fields that are zero unless the file section is recorded in interleaved mode. Because BP numbering starts at 1, the zero-based record indexes are 26 and 27, matching `rec[26]` and `rec[27]`. The inspector rejects either non-zero value with `INTERLEAVED_UNSUPPORTED`; targeted synthetic tests cover each byte independently and verify that input bytes are unchanged. Interleaved layouts remain unsupported.

**ECMA-119 volume-space text (checked 2026-10-22):** *ECMA-119, 5th edition (December 2024)*, §9.4.9 (p. 26) defines Volume space size (BP 81 to 88) as a 32-bit number of logical blocks in which the volume space of the volume is recorded. The inspector reads this field in both-endian form, rejects an image smaller than the declaration, and bounds directory and file reads to the declared volume. An image larger than the declared volume is accepted; bytes beyond it are not treated as ISO 9660 content. This standard text does not explain layered PS2 media or the meaning of such extra bytes.

**ECMA-119 primary-namespace contract (text checked 2026-10-28, RPTP-REF-006):** §7.7.2 (pp. 9–10) places the descriptor sequence at logical sector 16 and permits repeated recordings of one PVD plus boot, supplementary/enhanced and partition descriptors. §9.1.2 (p. 21) assigns types 0, 1, 2, 3 and 255; 4–254 are reserved. §9.5.3 (p. 32) distinguishes supplementary type 2/version 1 from enhanced type 2/version 2. Table 4 (p. 24) fixes the PVD root record at 34 bytes; §9.4.31 (pp. 29–30) requires primary file-structure version 1. §§7.5.1–7.5.2 (p. 8) define file sections and concatenated lengths; §10.1.7/Table 10 (pp. 39–40) defines associated/record-format flags, reserved bits 5–6 and bit 7 as a non-final section. §10.1.13 (p. 41) requires zero identifier padding, while §10.1.14 leaves system-use bytes unspecified. The RPTP policy is primary-namespace metadata only: record auxiliary descriptor headers with explicit warnings, never follow their roots or execute boot records, reject reserved types/conflicting PVD copies and unsupported file layouts before lookup, and keep survey counts at directory-record level rather than claiming reconstructed files. `IsoInputBoundaryTests` independently defines the RPTP ASCII/terminal-NUL-only configuration policy, duplicate-key and quote rejection, raw-record limits including special entries, directory/survey byte budgets including padding, empty-range bounds and large-executable streaming; these are safety/test contracts, not PS2 hardware facts. This is not Joliet/Rock Ridge, partition, raw-sector or multi-extent support. Tests are defined in `tests/test_iso_inspector.py`; the official PDF text was extracted locally using Python's standard library because the PDF renderer was unavailable. No sealed implementation source was accessed.

**ECMA-119 directory data-length correction (checked 2026-10-29, re-probed 2026-10-30, RPTP-REF-006):** §7.4.5 (p. 8) defines the data length of a file section as the number of bytes in which the file section is recorded in the data space, and states that if this number is less than the number of bytes in the data space, the remaining bytes are ignored in interchange. §10.1.5 (p. 38) applies that data length to directory records. A directory data length therefore need not be a multiple of the 2048-byte logical block; the inspector accepts any positive length and rejects only zero. A 2026-10-30 read-only re-probe of the owner-authorized Downhill Domination (USA) image confirmed all 15 directories are non-aligned, with lengths from 216 to 44,464 bytes (root directory 990 bytes). The earlier R-028 resolution requirement of a block-multiple length was corrected; `test_accepts_non_block_aligned_directory_data_lengths` covers 114- and 990-byte synthetic directories, and a 100-byte truncation still fails `DIRECTORY_RECORD_CROSSES_BLOCK`. This is a general ISO 9660 rule, not a PS2-specific or compatibility claim.

**Final inspection-review contracts (checked 2026-10-28):** ECMA-119 §7.8.1.2 (pp. 10–11, `RPTP-REF-006`) requires unused bytes after the last directory record in a sector to be zero; both inspection and survey now reject nonzero tails, including hidden records. Printable-ASCII primary identifiers with special directory-only identifiers, exact case-insensitive matching of an explicitly versioned BOOT component, and pre-queue extent deduplication/budgeting are RPTP safety contracts defined by `IsoReviewRegressionTests`, not complete ISO identifier grammar or hierarchy validation. **ORI/XORI 64-bit logical immediate model (updated 2026-10-26):** Finding F1 from the P1 audit identified that `ORI` and `XORI` were previously modeled with low-32-bit truncation (`(rs OP imm) & 0xFFFFFFFF`), inconsistent with the 64-bit register model used by `AND`/`OR`/`XOR`/`NOR`/`SLT`/`SLTU`/`LUI`. In MIPS64 Architecture For Programmers Volume II-A (MD00087; `RPTP-REF-013`), `ORI` is defined as `GPR[rt] <- GPR[rs] OR zero_extend(immediate)` and `XORI` as `GPR[rt] <- GPR[rs] XOR zero_extend(immediate)` across the full register width; the zero-extended 16-bit immediate has upper bits zero, so bitwise OR and XOR preserve the upper bits of `rs`. `ANDI` (`GPR[rt] <- GPR[rs] AND zero_extend(immediate)`) zeroes bits 16..63. Tested in `tests/test_instruction_logical_width.py` with literal constants, oracle checks and native C++ lowerer execution; `tests/test_instruction_logical.py` and `tests/test_instruction_ori.py` updated. Generic MIPS64 reference; R5900-specific behavior is not cross-checked.

**Synthetic execution-harness contract (recorded 2026-10-29, RPTP-REF-001, RPTP-REF-002, RPTP-REF-003, RPTP-REF-005, RPTP-REF-014 and RPTP-REF-015):** `rptp::runtime::execute_loaded` sequentially executes only the documented synthetic subset — the Gate 0 instructions (`ADDIU`, `ADDU`, `LW`, `SW`, `BEQ`, `BNE`, `J`, `JAL`, `JR`, `NOP`) plus the catalogued extensions (`SLL`, `SLT`, `SLTU`, `SLTI`, `SLTIU`, `DADDIU`, `DADDU`, `SUBU`, `AND`, `OR`, `XOR`, `NOR`, `ANDI`, `ORI`, `XORI`, `LUI`, `LD`, `SD`, `BEQL`, `BNEL`, `BLEZL`, `BGTZL`, `BLTZL`, `BGEZL`, `BLTZALL`, `BGEZALL`) — and at most one delay-slot instruction after each control transfer, using the encodings and test-defined arithmetic model already recorded in [INSTRUCTION_CATALOG.md](INSTRUCTION_CATALOG.md). `LD` and `SD` require 8-byte alignment, read or write the low word at the effective address and the high word at address + 4, and fail with `EXEC_MEMORY_FAULT` on an unaligned or out-of-segment doubleword range; `SD` verifies the full eight-byte range before writing either word. `BEQL`/`BNEL` compare the full 64-bit register values; the zero-test likely forms compare the signed low 64 bits of `rs` with zero; a taken likely branch executes its delay slot once, while a not-taken branch still fetches and validates the delay-slot word but performs no register, memory or trace effect, does not count a step and continues at `pc + 8`; `BLTZALL`/`BGEZALL` write `r31 = pc + 8` unconditionally on both outcomes and reject `rs = 31` with `EXEC_UNSUPPORTED_INSTRUCTION` as an RPTP fail-closed policy. Successful halt means only that the next PC left every loaded segment; it is an RPTP harness convention, not a hardware reset, return-address or timing fact. The registered Gate 0 fixture stores to `0x00002000`, outside its single RX segment, so the loader-backed harness rejects it with `EXEC_MEMORY_FAULT`; differential tests use two-segment synthetic images with a declared writable data segment. Evidence is `runtime/tests/runtime_tests.cpp` and `tests/test_runtime_execution.py`, the latter comparing registers, memory writes, trace, step count and final PC against the Python oracle; the branch-likely cases cover both outcomes for all eight forms, register and memory nullification, unconditional link writes, `$zero`, 32-bit PC masking, trace/step accounting and `rs = 31` rejection. This is a synthetic differential-test vehicle, not a product interpreter, recompiler, kernel, boot path or compatibility claim.
