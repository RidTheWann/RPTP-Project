**ECMA-119 spec text (checked 2026-10-22):** Ecma International, *ECMA-119, 5th edition (December 2024)*, Table 8 (p. 37) assigns BP 27 to File unit size and BP 28 to Interleave gap size; §§10.1.8–10.1.9 (p. 40) define both as 8-bit fields that are zero unless the file section is recorded in interleaved mode. Because BP numbering starts at 1, the zero-based record indexes are 26 and 27, matching `rec[26]` and `rec[27]`. The inspector rejects either non-zero value with `INTERLEAVED_UNSUPPORTED`; targeted synthetic tests cover each byte independently and verify that input bytes are unchanged. Interleaved layouts remain unsupported.

**ECMA-119 volume-space text (checked 2026-10-22):** *ECMA-119, 5th edition (December 2024)*, §9.4.9 (p. 26) defines Volume space size (BP 81 to 88) as a 32-bit number of logical blocks in which the volume space of the volume is recorded. The inspector reads this field in both-endian form, rejects an image smaller than the declaration, and bounds directory and file reads to the declared volume. An image larger than the declared volume is accepted; bytes beyond it are not treated as ISO 9660 content. This standard text does not explain layered PS2 media or the meaning of such extra bytes.

**ECMA-119 primary-namespace contract (text checked 2026-10-28, RPTP-REF-006):** §7.7.2 (pp. 9–10) places the descriptor sequence at logical sector 16 and permits repeated recordings of one PVD plus boot, supplementary/enhanced and partition descriptors. §9.1.2 (p. 21) assigns types 0, 1, 2, 3 and 255; 4–254 are reserved. §9.5.3 (p. 32) distinguishes supplementary type 2/version 1 from enhanced type 2/version 2. Table 4 (p. 24) fixes the PVD root record at 34 bytes; §9.4.31 (pp. 29–30) requires primary file-structure version 1. §§7.5.1–7.5.2 (p. 8) define file sections and concatenated lengths; §10.1.7/Table 10 (pp. 39–40) defines associated/record-format flags, reserved bits 5–6 and bit 7 as a non-final section. §10.1.13 (p. 41) requires zero identifier padding, while §10.1.14 leaves system-use bytes unspecified. The RPTP policy is primary-namespace metadata only: record auxiliary descriptor headers with explicit warnings, never follow their roots or execute boot records, reject reserved types/conflicting PVD copies and unsupported file layouts before lookup, and keep survey counts at directory-record level rather than claiming reconstructed files. `IsoInputBoundaryTests` independently defines the RPTP ASCII/terminal-NUL-only configuration policy, duplicate-key and quote rejection, raw-record limits including special entries, directory/survey byte budgets including padding, empty-range bounds and large-executable streaming; these are safety/test contracts, not PS2 hardware facts. This is not Joliet/Rock Ridge, partition, raw-sector or multi-extent support. Tests are defined in `tests/test_iso_inspector.py`; the official PDF text was extracted locally using Python's standard library because the PDF renderer was unavailable. No sealed implementation source was accessed.

**Final inspection-review contracts (checked 2026-10-28):** ECMA-119 §7.8.1.2 (pp. 10–11, `RPTP-REF-006`) requires unused bytes after the last directory record in a sector to be zero; both inspection and survey now reject nonzero tails, including hidden records. Printable-ASCII primary identifiers with special directory-only identifiers, exact case-insensitive matching of an explicitly versioned BOOT component, and pre-queue extent deduplication/budgeting are RPTP safety contracts defined by `IsoReviewRegressionTests`, not complete ISO identifier grammar or hierarchy validation. The neutral `elf(5)` `p_align` paragraph (`RPTP-REF-003`, fetched 2026-10-28) states that 0/1 require no alignment; otherwise alignment is a positive integral power of two and `p_vaddr` equals `p_offset` modulo `p_align`. The inspector now checks that congruence and the synthetic fixture uses alignment 4 with offset 84 and virtual address `0x00100000`; tests explicitly accept 0/1/4/4096 boundaries and reject an incongruent 4096-byte case. This verifies selected metadata constraints, not page-size, address-space, native-loader or PS2-specific behavior. All five review findings were reproduced before their production fixes; the read-only agent review is not an independent provenance disposition.

**ELF32 read-only load-map contract (checked 2026-10-28, RPTP-REF-003):** The downloaded `elf(5)` text defines `Elf32_Addr` as an unsigned 32-bit program address; the `PT_LOAD` paragraph maps file bytes to the beginning of memory, defines additional `p_memsz - p_filesz` bytes as zero, and requires load headers in ascending `p_vaddr` order. `e_entry` is the initial control-transfer virtual address; `PF_X` denotes an executable segment. `ElfLoadMapTests` independently tests overflow rejection for every load segment, an exclusive end exactly at `2^32`, empty/adjacent/equal-address/nested ranges, original header indexes, file-backed versus zero-fill entry mappings and non-executable/ambiguous entry warnings. RPTP uses half-open byte ranges and rejects decreasing load addresses without repairing the table. Overlap is metadata with a warning: this reference does not establish a universal overlap prohibition or loading precedence. Mapping offsets are relative to the boot ELF, never host pointers or ISO offsets. The map does not allocate segment memory, materialize code, choose physical-address mappings, apply relocations or define PS2 memory conventions; the synthetic analyzer/parser remains separate. The red run failed before implementation and the focused inspector suite passed afterward; see [VERIFICATION_LOG.md](VERIFICATION_LOG.md).

**ORI/XORI 64-bit logical immediate model (updated 2026-10-26):** Finding F1 from the P1 audit identified that `ORI` and `XORI` were previously modeled with low-32-bit truncation (`(rs OP imm) & 0xFFFFFFFF`), inconsistent with the 64-bit register model used by `AND`/`OR`/`XOR`/`NOR`/`SLT`/`SLTU`/`LUI`. In MIPS64 Architecture For Programmers Volume II-A (MD00087; `RPTP-REF-013`), `ORI` is defined as `GPR[rt] <- GPR[rs] OR zero_extend(immediate)` and `XORI` as `GPR[rt] <- GPR[rs] XOR zero_extend(immediate)` across the full register width; the zero-extended 16-bit immediate has upper bits zero, so bitwise OR and XOR preserve the upper bits of `rs`. `ANDI` (`GPR[rt] <- GPR[rs] AND zero_extend(immediate)`) zeroes bits 16..63. Tested in `tests/test_instruction_logical_width.py` with literal constants, oracle checks and native C++ lowerer execution; `tests/test_instruction_logical.py` and `tests/test_instruction_ori.py` updated. Generic MIPS64 reference; R5900-specific behavior is not cross-checked.
